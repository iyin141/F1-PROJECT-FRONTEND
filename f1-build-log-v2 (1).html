00 — What This Is

THE PRODUCT IN ONE PARAGRAPH

An F1 race analytics platform. Not a stats site. Not a fantasy tool. A platform where fans and analysts can understand what actually happened in a race — visually, clearly, and at a depth that broadcast coverage never reaches. The MVP is three pages. That is the entire product at launch.

3
Pages in MVP
Season Hub, Race Detail, Race Analysis. Every feature of every page is defined in this document. Nothing else ships.
22
Backend Endpoints Ready
Django API is complete with DB-first persistence. All responses are typed, validated, and sub-200ms for completed races.
12
Endpoints Used in MVP
The MVP consumes 12 of the 22 available endpoints. The remaining 10 are untouched — available for v2 without any backend changes.
0
Lines of Code Inherited

01 — Page One

SEASON HUB

The entry point. Every user starts here. The goal of this page is to orient the user in the season and give them a clear path into any race.

01
Season Hub
/races/[year]
Page 1 of 3
The user lands here when they open the platform. They see the full race calendar for the current season and the championship standings at a glance. They can switch to any year from 1950 to present. Completed races link into the Race Detail page. This page answers one question — what is happening in this season?
Race Calendar
  • All rounds for the selected year as a card grid
  • Each card — round number, race name, circuit, country, date
  • Status indicator — completed, upcoming, or in progress
  • Completed races are clickable, link to Race Detail
  • Upcoming races show a non-interactive state
  • Cards stagger in with GSAP on page load
Championship Standings
  • Driver standings — position, name, constructor, points, wins
  • Constructor standings — position, name, points, wins
  • Both default to showing top 5 with a show more toggle
  • Both standings load in parallel with the calendar
  • Year selector changes all three data sets simultaneously
Year Selector
1950 → Current Season
Input clamped at 1950 minimum, current year maximum. Changing year reloads calendar and both standings.
Data Source
DB-First · Live Fallback
Completed seasons read from Supabase. Current season in progress falls back to live FastF1 where DB is not yet populated.
Render Model
Server Component
All three data sets fetched server-side. Page arrives with data in HTML. No client-side loading spinners for primary content.
02 — Page Two

RACE DETAIL

Everything that happened at a single race weekend. The user arrives here from the Season Hub after clicking a completed race. This page answers — what happened at this race?

02
Race Detail
/races/[year]/[round]
Page 2 of 3
A full breakdown of a single race weekend across four tabs. The user can read the race narrative on the Overview tab, check the full results, inspect qualifying gaps, and review practice session data — all in one place. For completed races, a prominent link leads into the Race Analysis page.
Race Header
  • Race name, circuit name, country, date, round number
  • Country flag derived from country name
  • Breadcrumb back to Season Hub
  • Analysis page entry point — visible for completed races only
Overview Tab
  • Podium block — P1, P2, P3 displayed prominently with driver and constructor
  • Fastest lap — driver and lap time
  • Safety car count — derived from incidents data
  • Weather summary — air temp, track temp, rainfall yes/no
  • Incidents waterfall — retirements and safety car events in lap order
Results Tab
  • Full finishing order for all drivers
  • Position, driver name, constructor, points scored
  • Gap to winner for all classified finishers
  • Fastest lap indicator on the relevant driver
  • DNF and retirement status shown for non-finishers
Qualifying Tab
  • Full qualifying order — all drivers, all sessions
  • Q1, Q2, Q3 times per driver where applicable
  • Gap to pole position column
  • Q1 and Q2 elimination indicated visually
Practice Tab
FP1 · FP2 · FP3 Switcher
Session switcher between practice sessions. Each shows full results — position, driver, best lap time, total laps completed.
Tab System
Radix Tabs — Fully Styled
Radix UI Tabs primitive. Keyboard navigable, accessible, fully styled — no inherited Radix visuals. Tab state held in URL param for shareability.
Render Model
Server + Client Hybrid
Core data (results, qualifying) fetched server-side. Practice session switching is a client interaction — fetches only the requested session on demand.
Race Replay Tab — Lap-by-Lap Simulation
What It Shows
  • A vertical leaderboard of all 20 drivers updating lap by lap
  • Driver positions reorder with GSAP animation when overtakes happen
  • Gap to leader and gap to next car shown as live numbers per lap
  • Compound badge per driver updates when a pit stop is made
  • Safety car banner appears when track status goes SAFETY_CAR
  • Retirements fade a driver out of the board with a DNF label
  • Lap counter at the top — total laps shown as progress
Controls and Behaviour
  • Scrubber — drag to any lap in the race instantly
  • Play / Pause — auto-advance through laps at adjustable speed
  • Speed selector — 1x, 2x, 4x playback rate
  • All race data pre-loaded on page — no per-lap API calls during playback
  • GSAP timeline drives all position and gap animations
  • Available for completed races only — same gate as the Analysis page
Backend Endpoints
4 Endpoints · No Extra Backend Work
Endpoint 20 (positions per lap), Endpoint 19 (incidents for SC and DNF laps), Endpoint 18 (pit stop laps for compound switches), Endpoint 9 (stints for starting compound). All already exist.
Animation Engine
GSAP Timeline · Scrubbable
Full race pre-loaded into a GSAP timeline. Scrubber maps to timeline progress. Position reorders use GSAP flip animations for smooth driver card movement.
Data Strategy
Pre-Load All · Play Offline
All four endpoints fire once on tab open. Full race data held in memory. Playback runs entirely from that snapshot — no requests during simulation.
V2 Extension
Circuit Map When X/Y Added
One backend change — adding X and Y coordinate channels to the telemetry extractor — upgrades this to a circuit map replay with cars moving around the track outline.
03 — Page Three

RACE ANALYSIS

The differentiator. This is what no other free platform provides at this quality level. Three analysis panels that turn raw FastF1 data into insights a fan can actually read and act on.

03
Race Analysis
/races/[year]/[round]/analysis
Page 3 of 3
Three independent panels, each answering a different analytical question about the race. Available for completed races only. Every panel loads independently — none blocks another. Each shows a skeleton state while its data loads. The user can interact with Panel 2 before Panel 1 has finished loading.
Panel 1 — Tyre Strategy Timeline
  • Chart type: D3 Gantt — horizontal bars per driver, race laps on X axis
  • Every driver on the grid on the Y axis, ordered by finishing position
  • Each stint is a coloured bar using the canonical compound colours
  • Pit stop events shown as vertical markers on each driver's lane
  • On hover — compound name, stint lap count, average lap time for that stint
  • GSAP animates each driver's bars drawing left to right in sequence on load
  • This is the headline visualisation of the entire platform
Panel 2 — Pace Comparison
  • Chart type: D3 line chart — lap number on X axis, lap time on Y axis
  • Driver selector — choose any two drivers from the race grid
  • Both drivers plotted simultaneously in distinct colours
  • Safety car laps rendered as a greyed-out background band
  • Pit lap markers shown on the X axis for both drivers
  • GSAP draws both lines simultaneously left to right on load
  • Changing driver selection re-fetches only the lap data and redraws
Panel 3 — Driver Consistency
  • Computed on the frontend — no extra API call, derived from lap data
  • Score = standard deviation of lap times per stint, normalised and inverted
  • Higher score = more consistent driver across the race
  • All drivers ranked by consistency score, displayed as cards
  • Each card shows — driver code, score, best lap, average lap, most used compound
  • Score numbers count up from zero using GSAP counter tween on load
  • This is the first computed metric that sets the platform apart from raw data sites
Page Behaviour
  • Only accessible for completed races — unavailable state shown for upcoming races
  • All three panels load independently with skeleton states
  • Panels triggered by ScrollTrigger — animate only when scrolled into view
  • No panel blocks another from rendering
  • Render model: client-heavy — all D3 and GSAP runs in the browser
Compound Colours
Canonical · Platform-Wide
Same compound colour tokens used in every chart and label across the platform. Never hardcoded — always referenced from the design token system.
Chart Library
D3 v7 · SVG Rendered
All three panels use D3 for rendering. React holds the data and the ref. D3 owns the DOM inside the SVG element. GSAP animates the SVG attributes.
Data Loading
Heavy Endpoints · Opt-In
Laps endpoint and stints endpoint are opt-in heavy payloads. They only fire when the user navigates to the analysis page. Never pre-fetched.
Why This Page Is The Differentiator
F1 results tables and standings exist everywhere. The Tyre Strategy Timeline and Pace Comparison at this visual quality level — built on real lap-by-lap data, animated, interactive — do not exist as a free product. The Driver Consistency Score is a computed metric that no raw data site provides. This page is why the platform exists.

06 — Motion Ownership

FRAMER VS GSAP

Two motion libraries with clear, non-overlapping ownership. The same element is never animated by both. Framer owns React-component-level motion. GSAP owns DOM and SVG-level motion.

Framer Motion
React Component Layer
  • Page transitions — fade + translate on every route change
  • Component mount and unmount — cards, panels, modals
  • Staggered list reveals — race cards, standings rows, consistency cards
  • Skeleton to content fade when data arrives
  • Layout animations when list order changes
GSAP + ScrollTrigger
DOM and SVG Layer
  • Tyre strategy bars drawing left to right in sequence
  • Pace comparison lines drawing simultaneously from left
  • Consistency score numbers counting up from zero
  • Scroll-triggered panel entrances — chart animates only when in viewport
  • Future: race position simulation timelines with scrubber control
The Non-Conflict Rule
Framer Motion wraps React components with motion.div — it operates at the component level. GSAP receives a ref and targets the DOM directly — it operates at the element level. They never animate the same element at the same time. As long as this rule holds there are no conflicts.

08 — Build Sequence

ORDER OF WORK

Five blocks. Each must be fully complete before the next starts. The sequence is not negotiable — infrastructure before UI, pages before analysis.

B1
Foundation
Project initialised. All libraries installed. CSS token file written — both dark and light variable sets. Tailwind wired to token variables. ThemeProvider written and root layout configured. All TypeScript types written for every API response used in the MVP. No UI components. No pages. Just the infrastructure everything else depends on.
First
B2
API Layer
All Next.js BFF route handlers written — one per backend endpoint used in the MVP. Base fetch client with error normalisation and timeout. All typed service functions written — getRaces, getRaceResults, getStints, getLaps, getWeather, getIncidents, and all others. Every API call is testable before any UI component exists.
Second
B3
Season Hub
Global header with theme toggle. Framer Motion page transition wrapper. Skeleton component. Race cards with GSAP staggered entrance. Standings tables with show more toggle. Year selector. Season Hub page live and verified against real backend data across multiple seasons.
Third
B4
Race Detail
Radix Tabs component fully styled. Race header with country flag. Overview tab — podium, fastest lap, safety car count, weather summary, incidents waterfall. Results table with DNF status. Qualifying table with gap-to-pole. Practice table with session switcher. Race Detail page complete.
Fourth
B5
Race Analysis
D3 and GSAP integration pattern established. Tyre Strategy Timeline built first — it is the most complex and the most important. Pace Comparison chart second with driver selector. Driver Consistency cards with computed score logic third. ScrollTrigger wired for all three panels. This block gets the most time. It is the reason the platform exists.
Fifth
Non-Negotiable Rule
B1 and B2 must be complete before any visual work begins. A component written against undefined types or without a working API layer is throwaway code. The infrastructure blocks exist so that everything written in B3 through B5 is correct on the first pass.
